**Phase exit criteria:**

## How to use this file

- Each task is sized for **one agent session**: ≤ ~500 changed lines, excluding test fixtures and snapshots.
- **Start every task by writing failing tests** derived from the cited spec section. Then implement. Then make sure `cargo test` passes.
- **Never invent syntax or semantics.** If the spec is ambiguous or silent, stop and record the question in the task's "Questions" section of the PR description, or append it to `docs/syntax-questions.md`.
- Mark tasks done by checking the box and adding the commit hash.
- 🔒 marks a **human gate**: the director reviews and approves before dependent tasks start.

## P0-02 🔒 — Syntax spec (`docs/spec/syntax.md`)

- [ ] Done (commit: …)

**Inputs:**
- `build.md` §3 and every code example in it
- `effects.md` §3.1, §4.1, §6.1–§6.2, §6.7–§6.8
- `ai.md` §5.1, §6.1, §10.1, §14.1

**Deliverables:** `docs/spec/syntax.md`, containing:

1. **Lexical grammar:**
   - identifiers (Unicode XID)
   - keywords: reserved vs. contextual (`dataset`, `threshold`, `samples`, `with`?)
   - integer literals (`1_000`, `0x`, `0b`) and floats
   - strings, triple-quoted strings, `b"…"` byte strings, `prompt` literals, interpolation and `{{` escaping
   - comments and doc comments
   - operators and punctuation
2. **Newline rules:** when a newline terminates a statement and when it continues one (`build.md` §3.1), written as a precise algorithm.
3. **Full EBNF** for items, statements, expressions (with a precedence and associativity table), patterns, types, attributes, and generics, including `effect` generic parameters and `uses` effect arguments.
4. **Decisions required.** Each needs a recommendation plus a director decision:
   - **Generic call syntax in expressions:** `ai.generate<T>(…)` vs. comparison `a < b`. Recommended: speculative parse. After a path or field, try parsing `<` Types `>` and accept it only if immediately followed by `(` or `::`/`.`; otherwise backtrack and parse as an operator (C# approach).
   - **Map literals:** `{k: v}` collides with blocks. Recommended: Swift-style `[k: v]`, with `[:]` for an empty map. Update the `build.md` examples accordingly.
   - **Set literals:** recommended none; use `Set.of([...])`.
   - **Struct construction** with call syntax `User(name: "a")`: confirm. No brace literals, which avoids the Rust block ambiguity.
   - **Lambda syntax:** `fn(x) { … }` only, or also a short form (`build.md` §11 Q6). Recommended: `fn` only for v0.
   - **`...` hole expression:** recommended. `...` is a valid expression and item body **only** when parsing with `allow_holes` (doc-example mode, P0-17). Otherwise it's error E0010.
   - **Attribute placement:** on items, fields, variants, and parameters. Confirm that `@name(args)` on the preceding line or inline is equivalent.
   - **`for` desugaring:** calls a concrete `next()` method (`ai.md` §8).
   - **Visibility:** `pub` only for v0 (no `pub(crate)`).
   - **Module and `use` syntax:** file = module; `use a.b.{c, d as e}`.
5. An appendix listing every example in `build.md` that would change under these decisions.

**Acceptance:** director approval. `build.md`'s examples are updated to match (e.g. map literals). `build.md` §11 Q6 and the new syntax questions are closed with decision records in `docs/decisions/`.
**Size:** M (documentation). **Gate:** P0-05 onward wait for this.

## P0-04 — UI test harness

- [ ] Done (commit: …)

**Inputs:** `build.md` §5.2 (`tests/ui`), §9.
**Deliverables:**
- A `tests/ui` runner, as a `nova_cli` integration test or a dedicated `xtask`:
  - walks `tests/ui/**/*.nova`

- **Inline annotations:**

  - unannotated diagnostics fail the test
  - annotations that don't match a diagnostic fail the test
- A `tests/ui/README.md` documenting the format.

**Acceptance:** self-tests with fixtures that intentionally pass and fail. Until a parser exists, the harness runs against a stub "parser" that emits a diagnostic for a magic token.
**Size:** M.

## P0-05 — Lexer: tokens and trivia

- [ ] Done (commit: …)

**Inputs:** `syntax.md` lexical grammar (P0-02).
**Deliverables (`nova_syntax::lexer`):**
- A `SyntaxKind` enum covering all tokens and future node kinds, organized for rowan.
- A `logos`-based lexer producing `(SyntaxKind, len)` with **full fidelity**: whitespace, newlines, and comments are trivia tokens. Concatenating the token texts reproduces the input exactly.
- Doc comments (`///`) are distinct tokens.
- Keywords: reserved vs. contextual. Contextual keywords lex as `IDENT`, and the parser recognizes them.
- Number literals with separators and bases; float exponent forms.
- Error tokens for invalid characters, with E0001.

**Acceptance:**
- A table-driven test per token kind.
- Property test (proptest): `lex(s).concat() == s` for arbitrary strings.
- Every keyword from `syntax.md` is covered.

**Size:** M.

## P0-06 — Lexer: strings, interpolation, prompt literals

- [ ] Done (commit: …)

**Inputs:** `syntax.md` (strings), `build.md` §3.1, `ai.md` §5.1.
**Deliverables:**
- Lexing of `"…"`, `"""…"""`, `b"…"`, `prompt"…"`, `prompt"""…"""`.
- Interpolation: string tokens split into `STRING_START`, `STRING_TEXT`, `INTERP_START` (`{`), …expression tokens…, `INTERP_SPEC` (`:inline`), `INTERP_END` (`}`), `STRING_END`. Nested braces inside interpolated expressions are tracked.
- `{{` and `}}` escapes; standard backslash escapes; `\u{…}`. Invalid escapes → E0002. Unterminated string → E0003, recovering at end of line (for single-line strings) or end of file (for triple-quoted).
- A dedent algorithm for triple-quoted strings, implemented as a pure function used later by lowering (not at lex time). Lexing stays lossless.

**Acceptance:**
- Tests: nested interpolation (`"a {f("{x}")} b"`), `:inline`, escapes, unterminated recovery, `prompt` prefix adjacency (`prompt "x"` with a space is an identifier followed by a string).
- Dedent golden tests.

**Size:** M.

## P0-07 — Parser infrastructure

- [ ] Done (commit: …)

**Inputs:** `syntax.md` newline rules.
**Deliverables (`nova_syntax::parser`):**
- An event-based parser, in the style of rust-analyzer:
  - the parser emits `Start(kind)`, `Token`, `Finish`, `Error(msg, code)` events
  - a tree builder produces a rowan `GreenNode`
  - trivia is attached by the builder (leading comments and doc comments attach to the following item)
- A token source with lookahead `nth(n)`, skipping trivia but exposing "a newline precedes this token" as a flag. This is how newline-sensitivity works.
- Helpers:
  - `expect`, `eat`, `at`, `at_ts(TokenSet)`
  - `err_recover(msg, recovery: TokenSet)`
  - marker API (`start()`, `complete()`, `precede()`)
  - checkpoints for speculative parsing (needed for generic calls, per the P0-02 decision)
- A statement-termination helper implementing the `syntax.md` newline rules.
- `parse(text) -> Parse { green, errors }`. No AST yet. A `SyntaxNode` debug dump format for snapshots.

**Acceptance:**
- Unit tests of the marker API.
- A toy grammar (a list of identifiers separated by newlines) round-trips losslessly.
- A newline-continuation table test from `syntax.md`.

**Size:** M.

## P0-16 — Error recovery hardening and fuzzing

- [ ] Done (commit: …)

**Inputs:** all parser tasks.
**Deliverables:**
- A `cargo fuzz` target (or a proptest generator if fuzzing isn't available in CI) asserting, for arbitrary input:
  - no panic
  - lossless round trip (`tree.text() == input`)
  - parse time linear-ish (fails if over 50 ms per KB)
- A **corpus mutation test:** take every valid fixture, delete or duplicate random tokens, and assert no panic and at least one error.
- Recovery improvements found by fuzzing. Each fix comes with a minimized regression fixture in `tests/ui/syntax/recovery/`.
- A diagnostic quality pass: each parser error has a code (E0001–E0099) registered in `errors.md`, a primary label, and where helpful a `help:` line.

**Acceptance:** 10 minutes of fuzzing without findings in a CI nightly job (or 100k proptest cases in a normal test run); 20+ recovery fixtures.
**Size:** M.

## P0-17 — Doc-example extraction test

- [ ] Done (commit: …)

**Inputs:** P0-02 hole decision; P0-04 harness.
**Deliverables:**
- A test, `cargo test -p nova_syntax --test doc_examples`, that:
  1. Extracts every fenced block tagged `nova` from `docs/build.md`, `docs/spec/*.md`, and `docs/plan.md`. Blocks tagged ```` ```nova,ignore ```` are skipped, and each such block must have a nearby reason comment.
  2. Parses each block in `allow_holes` mode, trying item level first, then statement or expression level (wrapping it in a synthetic `fn __doc() { … }`).
  3. Fails with `file:line` of the block and the diagnostics.
- `plan.md` examples that conflict with `build.md` decisions (`error` keyword, `agent`, `api`, `from … select`, `actor`, `supervisor`, `sandbox`, `pure fn`, `schema`) are tagged `nova,ignore` with the reason "superseded by build.md". This makes the divergence explicit.

**Acceptance:** the test passes on the current docs; CI runs it; adding a broken example to a doc fails CI.
**Size:** S–M.
